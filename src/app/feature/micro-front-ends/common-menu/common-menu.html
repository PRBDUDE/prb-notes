Using micro frontend technology, how do I share a menu across multiple frontend applications

Sharing a menu across micro frontends (MFEs) is one of the most common architectural hurdles. You want a consistent user experience without forcing every team to redeploy when a menu link changes.

Here are the three most effective industry patterns to achieve this, ranked from "most flexible" to "easiest to implement."

1. Module Federation (The Modern Standard)

If you are using Webpack 5, Vite, or RSpack, Module Federation is the go-to solution. It allows one application to dynamically export a component (the Menu) and others to consume it at runtime.

  • How it works:
    1. Create a "Shell" or "Utils" MFE that contains the Menu component.
    2. Expose the component in the webpack.config.js.
    3. Remote applications "import" it as if it were a local library.
  • Pros: Seamless integration; feels like writing standard React/Vue; no page reloads.
  • Cons: Requires a shared build tool (e.g., all apps must use Webpack or a compatible plugin).

2. Shared Web Components (The Framework Agnostic Way)

If your MFEs use different frameworks (e.g., a React Header in an Angular app), Web Components are your best friend.
  • How it works:
    1. Build your menu using the Custom Elements API.
    2. Bundle it into a single JavaScript file hosted on a CDN.
    3. Each MFE includes the script tag and uses the custom tag:
      <main-menu></main-menu> .
  • Pros: Framework independent; completely decoupled versioning.
  • Cons: Styling can be tricky (Shadow DOM); slightly more boilerplate code.

3. The "App Shell" Orchestrator

Instead of sharing the menu into the apps, you put the apps inside the menu. This is the architecture used by libraries like single-spa.
  • How it works: * The App Shell (the container) is responsible for the Header, Sidebar, and Footer.
    • It defines a "slot" or "region" where the micro frontends are mounted based on the URL.
  • Pros: Centralized control; MFEs don't need to worry about the menu at all.
  • Cons: The Shell becomes a single point of failure; requires careful routing coordination.

Key Technical Considerations

Regardless of the method you choose, you’ll need to handle these two "gotchas":

State Synchronization: If the menu needs to show "Logged in as: User," use a lightweight shared state like a browser CustomEvent or a shared Redux/Zustand store if they live on the same window object.

Routing: Ensure that clicking a link in the shared menu triggers the History API (pushState) so that all micro frontends are aware of the URL change without a hard refresh.

Note: Avoid using NPM packages for shared UI components if you want to update the menu frequently. If you use a package, you’ll have to re-build and re-deploy every single MFE just to change one menu link!
